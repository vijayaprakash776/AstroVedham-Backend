# ASTROVEDHAM IMPLEMENTATION PLAN

This document outlines the detailed design and migration roadmap to secure the AstroVedham platform, eliminate security vulnerabilities (authentication gaps, IDORs, client-side pricing manipulation, and order number generation race conditions), populate a robust backend-driven Service Catalog, align the Admin Panel's report distribution mechanism, and connect the Flutter mobile app client securely.

---

## Current Architecture
- **Backend:** Node.js + Express + TypeScript + Prisma ORM + PostgreSQL.
- **Admin Panel:** Vite + React + TypeScript + Axios (proxied to port 3000 locally via devServer).
- **Flutter Client:** Standard mobile client consuming the API via the `Dio` HTTP library, utilizing local persistence via a storage manager (`LocalStorageService`).
- **State System:** Data definitions reside in `prisma/schema.prisma` mapping explicit relationships between `Admin`, `Customer`, and `Order` entries. Customer actions are entirely public, mapping queries purely through incoming parameters such as `phone`.

---

## Critical Issues

1. **Missing Customer Authentication [CRITICAL]:** Customer routes do not require verification tokens, allowing arbitrary clients to fetch user order tallies and data histories via plain numeric inputs.
2. **Insecure Direct Object References (IDOR) [CRITICAL]:** Path values (`/orders/:orderNumber` and `/orders/:orderNumber/report`) are exposed without checking the context of the user sending the request.
3. **Client-Controlled Ordering Price [HIGH]:** Order ingestion trusts price numbers derived directly from the application layer body payload instead of resolving catalog models from the backend.
4. **Order Number Creation Race Condition [HIGH]:** Counter lookups via `prisma.order.count()` compute daily sequences prone to duplicated calculations under highly concurrent ordering traffic.
5. **Admin Hardcoded Localhost Links [MEDIUM]:** Download paths in React templates are hardcoded to `http://localhost:3000/`, breaking downloads when deployed across separate hosts or containers.

## Phase 1 — Database / Schema Changes

### Files to Modify
- `prisma/schema.prisma` (Add `Service` model, update `Customer` and `Order` definitions)

### Files to Create
- `prisma/migrations/[timestamp]_add_services_and_auth/migration.sql` (Auto-generated by Prisma)

### Database Changes
1. **New `Service` Model:**
   ```prisma
   model Service {
     id              String   @id @default(uuid())
     slug            String   @unique
     title           String
     description     String?
     price           Decimal  @db.Decimal(10, 2)
     active          Boolean  @default(true)
     displayPosition Int      @default(0)
     createdAt       DateTime @default(now())
     updatedAt       DateTime @updatedAt
     orders          Order[]
   }
   ```
2. **Updated `Customer` Model:** Add `otpHash` and `otpExpiresAt` columns for handling passwordless verification.
3. **Updated `Order` Model:** Connect a formal relation constraint to the new `Service` model using a `serviceId` foreign key.

### API Changes
- None during this infrastructure step.

### Migration Requirements
- Execute `npx prisma migrate dev --name add_services_and_auth` to sync the local PostgreSQL schema.

### Risks
- Disrupting existing data shapes if fields are defined as strictly required without fallback provisions.

### Tests
- Validate column visibility via Prisma Studio or run `npx prisma migrate status`.

### Rollback Considerations
- Use `npx prisma migrate resolve` or execute a baseline SQL script removing the `Service` table and newly appended authentication tracking columns.

## Phase 3 — Customer OTP Authentication

### Files to Modify
- `src/app.ts` (Mount the public customer authentication router)

### Files to Create
- `src/routes/authRoutes.ts` (Endpoints for passwordless authentication)
- `src/controllers/authController.ts` (Handle verification logic and token generation)
- `src/services/smsService.ts` (Abstract provider interface for SMS delivery)

### Database Changes
- Modifies `Customer` entries dynamically to refresh short-lived OTP hashes and validation windows.

### API Changes
- **`POST /api/v1/auth/send-otp` [NEW]:** Ingests phone information and generates a secure random 6-digit verification code.
- **`POST /api/v1/auth/verify-otp` [NEW]:** Validates the incoming code against the stored hash and returns a signed customer JWT.

### Migration Requirements
- None.

### Risks
- Lockouts or API request blocking if external rate limit configurations are tuned too aggressively.

### Tests
- Mock delivery cycles under `NODE_ENV=development` to expose codes inside JSON payloads or console windows for local testing.

### Rollback Considerations
- Disable the OTP lifecycle path by commenting out or removing the authentication route registrations inside the application entry point.

## Summary of Planned Structural Modifications

### API Changes

| Path | Type | Auth | Description |
|---|---|---|---|
| `/api/v1/services` | `GET` | None | Lists available catalog services and prices |
| `/api/v1/auth/send-otp` | `POST` | None | Triggers verification code generation |
| `/api/v1/auth/verify-otp` | `POST` | None | Validates OTP and returns a Customer JWT |
| `/api/v1/orders` | `POST` | Customer | Creates an order using the server-side service price |
| `/api/v1/orders` | `GET` | Customer | Fetches the authenticated customer's order history |
| `/api/v1/orders/:orderNumber/report` | `GET` | Customer | Securely downloads the owned report PDF |

### Database Changes
- **New Table:** `Service` containing tracking parameters for product variants.
- **Table Alterations:** Added `otpHash` and `otpExpiresAt` text columns to `Customer`. Added a `serviceId` relationship constraint field to the `Order` model.

### Flutter Changes
- **Networking Enhancements:** Interceptors update out-bound headers with customer JWTs upon verification.
- **Component Refactoring:** `review_details_screen.dart` updated to transmit `serviceSlug` instead of raw pricing figures. Added an OTP login wizard.

### Admin Changes
- **Component Updates:** `OrderDetails.tsx` modified to use relative paths derived from the system's global Axios baseURL configurations instead of hardcoded local hosts.

### Security Improvements
- Complete elimination of IDOR exploits via JWT identity resolving layers.
- Protection against unauthorized modifications to order pricing.
- Secure, token-guarded access to PDF reports.

### Migration / Rollback Plan
- Run standard Prisma migrate paths sequentially. If issues arise, apply rollback logic using target rollback SQL scripts.

### Remaining Infrastructure Requirements
- **SMS Gateway Integration:** An abstract interface layer will be established, leaving production SMS provider integration as a future infrastructure task.
- **Cloud Object Storage Wrapper:** The system will store PDFs locally within the server's filesystem for now. Migrating this storage layer to an external production cloud platform (such as AWS S3 or Google Cloud Storage) remains an open infrastructure requirement.
